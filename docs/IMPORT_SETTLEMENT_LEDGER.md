# 複数個口・返金・追徴・異通貨の輸入精算

rc.24では `POST /v1/import-settlement/ledger` とSDKの `reconcileImportSettlementLedger` を追加しました。加盟店サーバーに保存した注文と見積もりに対し、商品数量、個口、申告、納付、配送業者の請求・支払いと返金の証跡を注文単位で照合します。

従来の `POST /v1/import-settlement/reconcile` は1出荷・1申告・1請求、同一通貨の契約を維持します。新しい台帳APIでは、複数の申告・証跡をまとめて渡します。実際の納付、返金申請、送金、配送業者への指示は接続先の業務システムが実行します。

各申告について基本となる納付証跡と請求書を各1件指定し、追徴や減額を元の証跡に結び付けます。支払い証跡は複数指定できます。複数申告をまとめた配送業者の請求書は、元請求との対応を保存したうえで申告ごとの費目へ正規化して渡します。各証跡の `parcelIds` は、その申告に割り当てた個口の集合と一致させます。

## 商品と個口

発送前の `/v1/import-settlement/plan` は複数の商品明細を受け付けます。`parcelCount` が2以上の場合は `parcels` に個口IDと各商品の数量を指定します。すべての注文数量を過不足なく割り当て、同じ個口IDや個口内の商品IDを重複させないようにします。割当の変更は `scopeDigest` を変えるため、配送業者の受諾記録を取り直します。

精算台帳は商品と個口の割当、および出荷・申告の参照を保存します。少額基準や税額を個口ごとに自動分割する機能ではありません。見積もりは、実際の貨物の合算条件と申告条件を確認した注文の見積もりを使います。

## 証跡と差額

| 記録 | 確認内容 |
| --- | --- |
| 税関納付 | 申告と税目ごとの納付額。追加納付には元の証跡と追徴根拠を指定 |
| 税関還付 | 元の納付証跡との対応と、税目ごとの還付額 |
| 配送業者の請求 | 関税・輸入税と業者手数料を別の費目として記録 |
| 請求の減額 | 元請求との対応と、費目ごとの減額 |
| 支払い・返金 | 請求・支払証跡との対応と、実際に精算された金額 |

税関への納付と配送業者への支払いは独立して確認します。配送業者の請求に含まれる税金と、税関納付の税金を突き合わせ、輸入費用へ二重に加算しません。金額が0と確認できた費目も明示し、未確認の費目と区別します。

同じ証跡ID・同じ内容の再送は一度だけ数えます。同じIDで内容が違う証跡、別の注文・請求先・申告の証跡、参照先のない調整、過大な減額・返金、未来日の証跡は確認対象になります。元の記録を上書きせず、追加の証跡で調整を記録してください。

還付・減額・現金返金の記録は、参照する元の納付・請求・支払いと同じ原通貨で指定します。累計の返金額を原通貨と換算後の双方で確認します。為替変動により換算後の返金が元の換算額を超える場合は要確認とし、為替差損益の自動仕訳は行いません。

見積もりとの差額を確認して承認する場合は、その台帳の `ledgerDigest` と確認者・証拠を `varianceReview` に保存します。確認日は対象の証跡と為替の確認日以降で、現在日までに限ります。金額や証跡が変われば再確認が必要です。差額の承認で、不正な参照、数量不一致、証跡不足などを解消したことにはなりません。

## 異通貨精算

`fxRates` に、原通貨から精算通貨への整数比、換算対象期間、確認日、確認期限、出典・証拠参照、丸め方法を指定します。`purpose` は `import_settlement` に限定し、通関価格用や購入画面用の為替と区別します。各異通貨の証跡は使用するレートIDを明示します。

`numerator / denominator` は原通貨の主要単位1あたりの精算通貨の主要単位です。例えばUSDからJPYへの150円なら、`numerator: "150"`、`denominator: "1"` です。`validFrom` は含み、`validTo` は含みません。`reviewBy` は日本時間の当日終了まで有効です。

換算は整数演算で行い、`half_up`、`down`、`up` から指定した方法で精算通貨の最小単位へ丸めます。出力には元金額・換算額・換算日・使用したレートの証跡を残します。レート不足、逆方向のレート、確認期限切れ、対象日外のレートを検出した場合は精算を確定しません。自動的な市場レート取得や、逆数・第三通貨を使う換算は行いません。

## 結果の利用

`pending` は必要な証跡や精算がまだそろっていない状態、`needs_review` は不一致や入力間の矛盾、`reconciled` は渡された証跡の範囲で照合できた状態です。請求と納付がそろい、支払いが一部だけの場合は、確認済みの請求額・支払額・残高を表示して `pending` を返します。原本の真正性、加盟店の認証と注文所有権、証跡の保存・アクセス権は呼び出し元で確認します。

HTTPは既存のサービス認証、64KiBの入力上限、`Cache-Control: no-store` を使います。大きな注文は上限に合わせて運用上の処理単位を設計してください。SDKとCLIでも同じスキーマと照合処理を使います。

```sh
npm run build
npm run cli -- import-settlement-ledger examples/import-settlement-ledger.json 2026-11-18T03:00:00+09:00
```

同梱例は合成証跡による機能検証用です。実際の配送業者・税関・銀行の接続や、実注文での照合結果を示すものではありません。

## 実装の保守

公開スキーマと処理の入口は `src/import-settlement-ledger.ts` に保持します。内部の証跡検査・換算・参照検査は `src/settlement-ledger/evidence.ts`、申告別の集計と最終判定は `accounting.ts` に分けています。商品数量と個口の割当検査は `src/parcel-allocation.ts` を発送前確認と共有し、それぞれのAPIが従来のエラー形式へ変換します。

`tests/import-settlement-refactor.test.ts` はrc.24の整理前の出力を基準に、金額・配列順序・診断・例外・承認ダイジェストの互換性を確認します。内部処理の変更時は `npm run check:public` を実行し、税表パックを用いる配布物では `npm run check` も確認します。契約記録を更新するときは、挙動を変える理由と影響範囲をレビューしてください。
