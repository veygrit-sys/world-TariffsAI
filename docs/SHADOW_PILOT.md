# 国・地域間の実注文の並行検証

加盟店1社・宅配便1社・通常B2C一般雑貨を対象に、10 SKUと最初の連続30注文を目安にします。対象範囲を試験開始前に決め、保留になった注文を含めて記録します。購入者への請求や申告は加盟店・通関担当者の既存手順で行います。並行検証の見積額は内部比較に使います。

台帳の `route` は実際の発送国と仕向地を `JP-SG` のように記録します。商用対象の登録コード同士の異なる組み合わせに対応し、北朝鮮、南極、未登録コード、同一国の組み合わせを両端で除外します。国コードの受付範囲と、個々の貨物で実際に見積もれる税・手数料の範囲は別々に判定します。域内取引、特別領域、原産国、規制、税関への申告は貨物ごとの根拠を確認します。

## 記録手順

1. 加盟店・配送会社の組み合わせごとに、アクセス制御された場所にJSON台帳を置きます。初期形は `{"version":1,"merchantRef":"m-opaque","carrierRef":"c-opaque","orders":[]}` です。参照はランダム発行した内部識別子を使います。住所、氏名、電話、文書原本、自由記述は元システムに保管します。
2. 購入前に `sample: "live"`、方向、注文参照、SKU参照、データ版、基準日を記録します。SDKの `captureShadowQuote(quote)` へ `quotePilotShipment` の応答を渡し、その時点の `quote` を保存します。同じ注文・版の根拠と商品情報も権限管理下で保存します。後日価格を見て見積もりを書き換えると検証できなくなります。
3. 通関後、同じレコードの `observation` に輸入許可通知参照と実請求を追記します。既存の請求照合と同じ6費目を使い、その他の実請求は `other` に記録します。未請求・不明の費目は欠落のまま扱い、確認済みの0を区別します。同じ費目の複数行は元通貨・対象注文を照合した上で合算します。見積通貨と請求通貨が異なる取引は、既存の精算台帳で為替根拠を確定して同一通貨に正規化した場合に照合します。見積保留の注文にも請求を付けられます。その場合は架空の見積IDを作らず、請求の `estimateId` を省きます。
4. 人の作業時間が分かる場合は `reviewMinutes` に実測値を記録します。複数担当者の場合は合計です。未実測は省略し、実際に介入がなかった場合のみ0を記録します。1注文1行で、同じ注文に複数の行を追加するとエラーです。本番DBでは加盟店・配送会社・sample・注文IDに一意制約を置き、請求の追記は同じ見積IDを確認して更新します。
5. SKUの進捗を表示する場合は任意の `products` に `sample,route,skuRef,classification` を記録します。分類状態は `unreviewed`、`candidate`、`confirmed` のいずれかです。確認済みには数字のみの `nationalCode` と `reviewBy` を付け、担当者と根拠は元システムで保持します。分類の表示は登録時点の記録です。新しい見積もりには適用日と承認の再照合が必要です。

## 集計と表示

```sh
npm run build
node dist/cli.js shadow-ledger examples/shadow-ledger-world.json --synthetic --site
node dist/cli.js shadow-ledger private-evidence/shadow-ledger.json
node dist/cli.js shadow-ledger private-evidence/shadow-ledger.json --site
node dist/cli.js shadow-ledger examples/shadow-ledger.json --synthetic --site
```

通常実行は `live` のみを集計します。[日本向けの2件](../examples/shadow-ledger.json)と[複数仕向地の12件](../examples/shadow-ledger-world.json)はすべて合成で、通常実行の実績は0件です。複数仕向地の例では、SGDとGBPの担当者確認額を使った照合、英国向けの配送会社請求差0.75 GBP、複数仕向地の保留を再現します。これらの金額は集計機能の試験用です。`--synthetic` は合成のみを集計します。`--site` は注文とSKUの仮名、対象日、費目別の見積額・実請求、保留理由コード、登録済みの分類・次回確認日を加えます。原本・請求IDは出力しません。取引情報を含むため内部用の出力として管理します。既知の保留コード以外は表示で `OTHER_HOLD` にまとめ、元のプレビューで詳細を参照します。国別のコードでは、中国向けの年間枠、シンガポール向けの購入時GST納付情報の引継ぎ、ニュージーランド向けの郵便賦課金の購入者負担など、保留時に確認する項目を示します。

| 指標 | 分母・解釈 |
| --- | --- |
| 見積提示率 | 完全な輸入費用見積もりを発行できた注文数 ÷ 対象注文全体。保留を分母に含み、未観測では `null` |
| 費目別の独立計算一致率 | その費目でシステムが計算し、実請求も分かった件数のうち、金額が最小通貨単位まで一致した割合。担当者入力 `confirmed_amount` と確認済み適用外 `not_applicable` は別集計 |
| 過少見積額の最大値 | 全輸入費目の実請求が分かった注文について、実請求合計（追加費用を含む）から見積合計を引いた最大の正の差額。方向・通貨ごとに表示。購入時税、商品代金、基本送料は計算範囲外 |
| 関税0円に対する正の請求 | 関税を0と見積もり、実請求の関税が正だった注文数。差の法的理由は担当者が元明細で確認 |
| 確認時間 | 実測件数、合計・平均分。未入力の注文を平均から除外 |
| 10 SKU・30注文 | `pilots` に方向別の計画値、対象注文に含まれた異なるSKU数と注文数。商品マスタだけがある方向は0件で表示します。従来の `cnJpPilot` は引き続きCN→JPだけを返します。実証の進捗であり、本番提供の承認は別途必要 |

見積もりのない注文や請求の欠落を金額0に変換しません。1方向1注文を対象とする既存の[運用者レビュー](PILOT_LIVE_VALIDATION.md)とは独立して、継続的な品質をこの台帳で集計します。

国別の税制プレビューが一部費目だけを計算した場合、SDKの `captureCountryPreview(preview)` を使って `held` として保存します。通貨、税目、個別の見積額と根拠は元のプレビューに保持し、全費目をそろえて購入前に見積もりを提示できるようになった案件だけを `offered` に記録します。試験用データと実績は同じ注文番号でも別に集計します。商品を別方向に登録すると、仕向地ごとの分類確認記録が保持されます。
